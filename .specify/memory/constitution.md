# Money Control Constitution

## Core Principles

### I. Финансовая точность

- Денежные суммы MUST храниться и обрабатываться как целые числа в минорных единицах
  (копейки/центы) или как decimal фиксированной точности. Тип float/double для денег запрещён.
- Каждая сумма MUST иметь явную валюту (ISO 4217). Сложение сумм в разных валютах без явной
  конвертации запрещено.
- Правила округления MUST быть заданы явно и одинаково применяться во всех расчётах.
- Все расчёты бюджета, лимитов и остатков MUST быть детерминированными: одинаковые входные
  данные дают одинаковый результат.

**Обоснование**: пользователь принимает финансовые решения по цифрам приложения. Ошибка
в копейку подрывает доверие ко всему продукту.

### II. Приватность и безопасность финансовых данных

- Приложение MUST собирать только данные, необходимые для работающей функции. Каждое новое
  поле с персональными или финансовыми данными MUST быть обосновано в спецификации.
- Финансовые и персональные данные MUST шифроваться при передаче (TLS) и при хранении.
- Персональные данные, суммы и номера счетов MUST NOT попадать в логи, аналитику и сообщения
  об ошибках.
- Интеграции с банками MUST использовать доступ только на чтение и подключаться только после
  явного согласия пользователя. Пользователь MUST иметь возможность отключить интеграцию.
- Пользователь MUST иметь возможность экспортировать и полностью удалить свои данные.
- Данные пользователя MUST NOT передаваться третьим лицам для рекламы или продажи.

**Обоснование**: банковские выписки — одни из самых чувствительных данных человека.
Утечка или злоупотребление ими недопустимы.

### III. Объяснимые рекомендации

- Скоринговая модель и выбор метода бюджетирования (например, 50/30/20, недельные лимиты,
  конверты) MUST быть объяснимыми: пользователь видит, какие его данные повлияли на
  рекомендацию и почему.
- Правила скоринга MUST быть версионированы. Каждая выданная рекомендация хранит версию
  правил, по которой она получена.
- Пользователь MUST иметь возможность не согласиться с рекомендацией и выбрать другой метод.
- Приложение MUST NOT выдавать персональные инвестиционные советы и MUST явно сообщать, что
  рекомендации носят информационный характер.

**Обоснование**: «чёрный ящик», который решает за человека, как ему жить, вызывает
недоверие. Объяснимость делает рекомендации полезными и проверяемыми.

### IV. Test-First для доменной логики (NON-NEGOTIABLE)

- Для скоринга, расчёта бюджетов и лимитов, оценки соблюдения бюджета, парсинга импорта и
  начисления игровых наград тесты MUST быть написаны до реализации и сначала падать
  (Red → Green → Refactor).
- Каждый поддерживаемый формат импорта MUST иметь набор фикстур с обезличенными примерами,
  включая граничные и ошибочные случаи.
- Каждый метод бюджетирования MUST иметь тесты с эталонными примерами расчёта.

**Обоснование**: доменная логика — ядро ценности продукта. Ошибка в ней тихо даёт человеку
неверный финансовый совет.

### V. Импорт данных как контракт

- Все источники данных (ручной ввод, CSV, банковские выписки, банковские API) MUST
  приводиться к единой модели транзакции через отдельный адаптер для каждого источника.
- Импорт MUST быть идемпотентным: повторная загрузка тех же данных не создаёт дубликаты.
- Строки, которые не удалось разобрать, MUST NOT отбрасываться молча. Пользователь видит,
  что не импортировано и почему.
- Импорт MUST NOT изменять уже подтверждённые пользователем данные без его согласия.

**Обоснование**: качество аналитики и рекомендаций не может быть выше качества входных данных.

### VI. Этичная геймификация

- Геймификация MUST поощрять соблюдение бюджета и регулярные проверки (еженедельные или
  ежемесячные), а не рост трат или время в приложении.
- Тексты и механики MUST NOT стыдить пользователя за перерасход. Выход за бюджет показывается
  нейтрально и вместе с конкретным следующим шагом.
- Механики MUST NOT использовать манипулятивные паттерны: искусственную срочность, потерю
  прогресса за пропуск, платные ускорения.
- Пользователь MUST иметь возможность отключить игровые элементы без потери функциональности.

**Обоснование**: цель — устойчивая финансовая привычка. Давление и чувство вины её разрушают.

### VII. Простота и поэтапность

- Каждая функция MUST поставляться как независимо полезный срез (MVP-first). Сначала ручной
  ввод и CSV, затем выписки, затем банковские интеграции.
- Новая зависимость, сервис или слой абстракции MUST быть обоснованы в плане реализации.
  Принцип YAGNI применяется по умолчанию.
- Сложность сверх необходимой MUST быть записана в разделе «Complexity Tracking» плана.

**Обоснование**: продукт широкий. Без жёсткой поэтапности он не дойдёт до первого
работающего релиза.

## Продуктовые и технические ограничения

- **Язык и регион**: интерфейс сначала на русском. Тексты MUST быть вынесены для
  локализации. Валюта по умолчанию — RUB, но модель данных MUST поддерживать мультивалютность.
- **Платформа**: первая версия — Telegram Mini App (Bot API ≥ 9.0): клиентское веб-приложение
  на TypeScript (strict) и React, статический хостинг по HTTPS. Доменная логика MUST жить в
  модуле без зависимостей от UI, Telegram и хранилища, чтобы её можно было переиспользовать
  на других платформах и на сервере.
- **Хранение**: данные пользователя хранятся только на устройстве и в зашифрованном виде.
  Telegram CloudStorage и любые серверные хранилища для пользовательских данных запрещены,
  пока это ограничение не изменено поправкой.
- **Доступность**: ключевые сценарии (ввод дохода, просмотр бюджета, проверка статуса)
  MUST быть доступны с клавиатуры и экранных читалок и MUST корректно работать на
  мобильной ширине экрана.
- **Регуляторика**: обработка персональных данных MUST соответствовать применимому
  законодательству о персональных данных (например, 152-ФЗ, GDPR — для рынков, где
  запускается продукт).
- **Производительность**: импорт CSV на 10 000 строк MUST завершаться и показывать
  результат не более чем за 10 секунд на типичном устройстве пользователя.

## Процесс разработки и контроль качества

- Каждая функция проходит цикл Spec Kit: `/speckit-specify` → (`/speckit-clarify`) →
  `/speckit-plan` → `/speckit-tasks` → `/speckit-implement`.
- Каждая функция разрабатывается в отдельной ветке `NNN-short-name` и вливается в `main`
  только после ревью.
- Ревью MUST проверять соответствие принципам I–VII. Нарушение без записи в «Complexity
  Tracking» блокирует слияние.
- Перед слиянием MUST проходить все тесты, линтер и проверка типов.
- Спецификации описывают «что» и «зачем» без деталей реализации. Технические решения
  принимаются в плане.

## Governance

- Конституция имеет приоритет над остальными практиками и документами проекта.
- Поправки вносятся через `/speckit-constitution` отдельным коммитом с описанием причины
  и обновлением версии.
- Версионирование: MAJOR — удаление или переопределение принципа; MINOR — новый принцип
  или существенное расширение раздела; PATCH — уточнения формулировок.
- Каждый план реализации MUST содержать раздел «Constitution Check». Отступления
  допускаются только с обоснованием в «Complexity Tracking».
