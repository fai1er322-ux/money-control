# Research: Финансовый профиль и рекомендация метода бюджетирования

**Feature**: `001-budget-method-recommendation` | **Date**: 2026-11-17

## R1. Платформа

- **Decision**: Telegram Mini App — статическое веб-приложение (SPA), которое открывается из бота
  Money Control через Menu Button. Своего сервера в этой функции нет.
- **Rationale**: не нужна установка и регистрация. Пользователь уже авторизован в Telegram.
  Бот в будущем даст напоминания о еженедельной сверке (геймификация). Статический фронтенд
  совместим с FR-020: данные никуда не отправляются.
- **Alternatives considered**: PWA в браузере (браузер может стереть localStorage и IndexedDB,
  нет канала напоминаний); нативное мобильное приложение (дольше в разработке, нужна
  публикация в сторах — противоречит принципу VII на старте).

## R2. Хранение данных только на устройстве

- **Decision**: зашифрованный блок данных хранится в `Telegram.WebApp.DeviceStorage`, ключ
  шифрования — в `Telegram.WebApp.SecureStorage`. Если клиент не поддерживает эти API,
  используется запасной путь: IndexedDB для данных и неизвлекаемый (non-extractable) ключ
  WebCrypto в IndexedDB. CloudStorage не используется.
- **Rationale**:
  - DeviceStorage (Bot API 9.0): постоянное локальное хранилище, 5 МБ на пользователя и бота,
    доступно только этому боту. Данных первой функции — единицы килобайт.
  - SecureStorage (Bot API 9.0): до 10 элементов, хранится в iOS Keychain / Android Keystore,
    шифруется в покое. Подходит для одного ключа. Если ключ не найден, `getItem` сообщает, можно
    ли его восстановить, а `restoreItem` запрашивает разрешение пользователя.
  - CloudStorage хранит данные на серверах Telegram — нарушает FR-020.
- **Risk**: официальная документация не перечисляет клиенты, где работают DeviceStorage и
  SecureStorage (Desktop, Web). Поэтому адаптер хранения определяет возможности при запуске
  (`isVersionAtLeast('9.0')` и проверка наличия объектов) и выбирает режим. В задачах
  предусмотрен спайк: проверка на iOS, Android, Telegram Desktop и Telegram Web.
- **Alternatives considered**: только IndexedDB (Telegram WebView на iOS может очищать данные
  сайта); хранение без шифрования (нарушает принцип II).

## R3. Шифрование

- **Decision**: AES-GCM 256 через WebCrypto (`crypto.subtle`). Новый случайный IV (12 байт) на
  каждую запись. В зашифрованный конверт входят версия формата, IV и шифртекст.
- **Rationale**: встроено в браузер, без зависимостей; аутентифицированное шифрование ловит
  повреждение данных.
- **Alternatives considered**: libsodium (лишняя зависимость); шифрование паролем пользователя
  (лишний шаг для первой версии; может появиться как опция).

## R4. Язык и фреймворк

- **Decision**: TypeScript 5.x (strict), React 19, Vite. Telegram API — через официальный скрипт
  `telegram-web-app.js` и собственную тонкую типизированную обёртку.
- **Rationale**: зрелый стек для SPA; React хорошо подходит для многошаговой анкеты. Одна
  обёртка над `window.Telegram.WebApp` проще, чем сторонний SDK, и легко подменяется моком в
  тестах (принцип VII).
- **Alternatives considered**: сторонние SDK для Mini Apps (лишняя зависимость с частыми
  переименованиями пакетов); Svelte/Vue (меньше значимых отличий для этой задачи).

## R5. Деньги и округление

- **Decision**: суммы — целые числа в копейках (`number`, проверка `Number.isSafeInteger`).
  Доли методов — в базисных пунктах (1 % = 100 б.п.). Каждая часть плана вычисляется как
  `floor(доход × доля / 10 000)`. Остаток от округления добавляется в часть «накопления».
- **Rationale**: принцип I; безопасного диапазона `number` (до 9·10^15 копеек) достаточно для
  личного бюджета. `bigint` усложнил бы сериализацию и UI без пользы.
- **Alternatives considered**: decimal-библиотека (лишняя зависимость при только целочисленных
  операциях); `bigint`.

## R6. Скоринг

- **Decision**: прозрачная таблица правил с баллами (`scoring-rules` версии `1.0.0`). Каждое
  правило — условие на показатели профиля и баллы для методов. Итог метода — сумма баллов;
  при равенстве побеждает метод, стоящий выше в каталоге. Объяснение — 2–4 правила с
  наибольшим вкладом в выбранный метод. Полная таблица — в
  [contracts/scoring-rules-v1.md](contracts/scoring-rules-v1.md).
- **Rationale**: принцип III (объяснимость, версионирование) и FR-007 (детерминизм).
- **Alternatives considered**: обучаемая модель (нет данных, необъяснима); дерево решений
  (сложнее объяснять вклад нескольких факторов).

## R7. Валидация и формат экспорта

- **Decision**: Zod 4 для схем анкеты и файла экспорта. Экспорт — JSON-файл с версией формата
  ([contracts/export-file.schema.json](contracts/export-file.schema.json)), отдаётся через
  `Telegram.WebApp.downloadFile` или ссылку для скачивания. Импорт — выбор файла.
- **Rationale**: одна схема даёт и проверку ввода, и типы TS, и проверку импортируемых файлов
  (принцип V, FR-021). Файл экспорта не шифруется: пользователь сам решает, где его хранить, и
  видит предупреждение об этом.
- **Alternatives considered**: ручные валидаторы (больше кода и ошибок); зашифрованный экспорт
  (ключ привязан к устройству — перенос стал бы невозможен).

## R8. Тестирование

- **Decision**: Vitest для доменного ядра и адаптеров; Testing Library для компонентов;
  Playwright для сквозных сценариев в браузере с моком `window.Telegram.WebApp`.
- **Rationale**: принцип IV; Vitest работает нативно с Vite.
- **Alternatives considered**: Jest (лишняя настройка под Vite и ESM).

## R9. Хостинг и бот

- **Decision**: статический хостинг по HTTPS (GitHub Pages или Cloudflare Pages). Бот создаётся
  через BotFather, его Menu Button открывает Mini App. Серверного кода у бота в этой функции нет.
- **Rationale**: принцип VII. Напоминания о сверке появятся вместе с функцией геймификации и
  потребуют сервер — это отдельное решение.
- **Alternatives considered**: свой сервер сразу (не нужен для FR текущей функции).

## R10. Идентификация пользователя

- **Decision**: `initData` и `user.id` не используются и никуда не сохраняются.
- **Rationale**: DeviceStorage и SecureStorage уже разделены по пользователю и боту. Без сервера
  проверить подпись `initData` нельзя. Меньше данных — меньше риск (принцип II).
